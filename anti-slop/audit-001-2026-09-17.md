# Anti-slop audit 001

Date: 2026-09-17  
Scope: Mailbox Mover desktop UI and user-facing copy  
Mode: AFTER  
Status: copy findings resolved; visual redesign reverted at owner request

## Context

No `DESIGN.md` or owner-supplied brand direction exists. Under R-37, the current interface is therefore a draft without direction. This audit does not invent a replacement style. It identifies the changes that need either owner direction or approval.

The screen's job is clear: collect three paths/settings, verify Outlook, and run a migration. The audit uses that workflow as the content hierarchy.

## Findings

### 1. HIGH: The shipped UI has no design direction

**Rules:** R-37, R-20, R-31  
**Evidence:** There is no `DESIGN.md`. The interface uses a generic blue system palette, system/Inter font stack, soft cards, rounded icon tiles, shadows, and a radial background without recorded product-specific reasons in `frontend/src/main.ts` and `frontend/src/style.css`.  
**Why it matters:** The result is functional but could be relabeled for another migration utility with little visual change. Antislop requires owner direction before a redesign can be treated as final.  
**Proposed fix:** Obtain one concise direction from the owner covering personality, palette, typography, and mood, then record explicit ENERGY / RHYTHM / MOTION dials in `DESIGN.md` before visual changes.

### 2. HIGH: “Already contains EML” creates contradictory source instructions

**Rules:** R-26, R-27, C-2, C-4  
**Evidence:** The toggle says “My source already contains EML files” and “import the working folder directly,” but the only EML path remains the field labeled “Temporary working folder.” The Thunderbird source card changes to “Skipped” while the working-folder placeholder still asks for an empty folder.  
**Why it matters:** Users cannot tell whether they should pick an existing EML folder or an empty temporary folder. The backend accepts an existing EML directory in this mode, so the interface does not describe the actual behavior.  
**Proposed fix:** When enabled, relabel the third card to “Choose your EML folder,” change its supporting copy and placeholder, and hide or disable settings that only apply to generated temporary files.

### 3. HIGH: The progress bar presents invented conversion progress

**Rules:** R-17, R-38, C-5  
**Evidence:** `renderProgress()` displays hard-coded values of 5%, 20%, and 95% when no measurable total exists. During mbox conversion the UI therefore shows a numeric percentage that is not calculated from real progress.  
**Why it matters:** A percentage implies measured completion. These numbers are decorative estimates, not evidence.  
**Proposed fix:** Use an indeterminate progress bar during preparation/conversion, then show a determinate percentage only during EML import when `current` and `total` are real.

### 4. HIGH: The source-help message replaces the error alert and cannot be dismissed

**Rules:** R-26, R-27, C-4  
**Evidence:** “Where is this folder?” writes informational content into `#form-alert`, changes its classes, and leaves it visible until another operation calls `clearError()`. The same region is also used for errors.  
**Why it matters:** Help and errors overwrite each other, and keyboard users have no explicit close action. The UI state is ambiguous.  
**Proposed fix:** Use a dedicated inline help disclosure under the source field or a keyboard-accessible dialog with a close button and Escape handling. Keep errors in a separate live region.

### 5. MEDIUM: Visual hierarchy is flattened by repeated card treatment

**Rules:** R-12, R-14, R-31, C-3  
**Evidence:** Source, Outlook, working folder, preferences, progress, readiness, and explanation all use bordered white cards with `shadow-sm` and similar radii. The repeated treatment makes setup steps, secondary guidance, and live progress look equally important.  
**Why it matters:** Users need the current blocking task and final migration action to dominate. Repeated elevation removes that hierarchy.  
**Proposed fix:** Keep one primary work surface, render secondary setup sections as flatter field groups, and reserve elevation for live progress or the current blocking step. Final shape depends on finding 1.

### 6. MEDIUM: Color and icon choices read as library defaults rather than product identity

**Rules:** R-01, R-04, R-29, R-31  
**Evidence:** Three differently colored icon tiles introduce primary blue, secondary cyan, and accent green. Nearly every control or status uses a Lucide icon. The CSS also adds a blue radial glow without a documented hierarchy or brand purpose.  
**Why it matters:** The palette and icon vocabulary feel assembled from framework defaults. The three setup steps do not need three semantic colors, and repeated thin-stroke icons add visual noise.  
**Proposed fix:** After direction is supplied, reduce setup steps to one core accent plus semantic status colors, remove decorative icons, and retain icons only where they improve recognition.

### 7. MEDIUM: The hero copy overpromises certainty

**Rules:** R-16, R-36, C-5  
**Evidence:** “Move your mail with confidence” is an unsupported reassurance. “Let the app handle conversion and import” is vague about what the user must keep open and what can fail.  
**Why it matters:** Migration software benefits from plain, procedural language, especially when Outlook COM and local CDO components impose real constraints.  
**Proposed fix:** Replace the headline and subcopy with direct task language, for example “Move Thunderbird mail into a Classic Outlook PST” and one sentence naming the three required choices.

### 8. MEDIUM: The UI uses AI-copy rhythm and vague microcopy in several states

**Rules:** R-02, R-16, R-36  
**Evidence:** Examples include “Ready when you are,” “Ready to move?”, “What will happen?”, “Migration needs attention,” and “safely expanded.” The success text uses an em dash: “Done — …”.  
**Why it matters:** These phrases add friendliness without adding instructions. Error states should say what failed and what action is available. The em dash violates the project's installed R-02 rule.  
**Proposed fix:** Use plain state labels such as “Setup incomplete,” “Migration stopped,” and “Could not continue.” Replace the success sentence with two short sentences or a colon.

### 9. LOW: The eyebrow label and arrow are decorative

**Rules:** R-06, R-08, R-31  
**Evidence:** “Guided migration” is uppercase with wide tracking above a heading that already describes the workflow. The primary button includes a right arrow in addition to a play icon.  
**Why it matters:** Both elements duplicate meaning and use recognizable generated-UI conventions.  
**Proposed fix:** Remove the eyebrow. Keep one relevant control icon at most, or use a text-only primary action.

### 10. LOW: Responsive behavior starts from a desktop-only minimum width

**Rules:** R-03, C-4  
**Evidence:** `body { min-width: 640px; }` forces horizontal overflow below 640 px, while form rows use non-wrapping flex layouts and the step indicator remains horizontal.  
**Why it matters:** Wails currently enforces a 900 px minimum window, so the defect is masked in the desktop shell. It still breaks browser development, narrow accessibility setups, and future window-size changes.  
**Proposed fix:** Remove the body minimum width, stack picker controls on narrow widths, and switch the process indicator to a compact or vertical form when space is limited.

### 11. LOW: UI typography has no stated reason and falls back to a generic default

**Rules:** R-06, R-20, R-31  
**Evidence:** The root stack begins with Inter but the project neither bundles Inter nor records why it fits a mail-migration utility. Most systems will therefore display the platform UI font.  
**Why it matters:** This is serviceable but not a deliberate product voice.  
**Proposed fix:** Choose and document typography after finding 1. A native Windows UI stack may be the right answer, but it should be an intentional fit for a Windows utility rather than an accidental fallback.

## What already works

- The interface is built around a real migration workflow rather than a landing-page template.
- Buttons, toggles, the PST selector, theme switch, collapse, cancellation, and folder actions have implementations.
- Loading, error, cancellation, and completion states exist.
- No fake testimonials, customer counts, performance claims, or filler data appear.
- Light and dark theme definitions are present.
- Product CTAs are specific: “Start migration,” “Check again,” “Stop safely,” and “Open EML folder.”

## Resolution

The owner approved the audit, then asked to retain the v1.0.1 visual design and apply copywriting fixes only. The attempted visual redesign was reverted. `frontend/src/style.css`, frontend dependencies, cards, colors, icon treatment, spacing, and layout remain unchanged from v1.0.1.

Applied copy changes:

- Replaced the unsupported reassurance in the main heading with the literal task: moving Thunderbird mail into Outlook.
- Named the three required choices and the requirement to keep Classic Outlook open.
- Replaced vague status text such as “Ready when you are,” “Ready to move?”, “What will happen?”, and “Migration needs attention.”
- Replaced “Stop safely” with the accurate action “Stop after current message.”
- Clarified existing-EML mode by changing the source description, third-step title, folder description, and placeholder when the toggle is enabled.
- Removed prohibited dash punctuation and ellipses from product copy, backend status messages, README text, and legacy script comments.
- Rewrote the source-folder help sentence without a decorative arrow.

Not applied at owner request:

- Findings 1, 5, 6, 9, 10, and 11 require visual changes, so the previous design remains.
- Finding 3 requires progress behavior changes rather than copy changes, so the existing progress presentation remains.
- Finding 4 requires interaction/layout changes, so the existing shared alert region remains.
